# Decisiones

Registro de decisiones tomadas con el usuario. **No las cambies sin que el usuario lo pida.** Si una decisión nueva reemplaza a otra, agrégala abajo y marca la anterior como reemplazada.

| # | Fecha | Decisión | Por qué / alternativas descartadas |
|---|---|---|---|
| 1 | 2026-10-10 | Frontend y backend separados en un monorepo (pnpm + Turborepo) | Separar responsabilidades y compartir tipos y validaciones. Una sola app con Next.js descartada. |
| 2 | 2026-10-10 | Backend con NestJS | Su estructura de módulos encaja con las secciones. Descartados Hono/Fastify (menos estructura) y Laravel (no comparte tipos con el front). |
| 3 | 2026-10-10 | Frontend con Next.js (App Router) + TypeScript, CSS Modules + variables CSS, Motion | Sin Tailwind: al usuario no le gusta el HTML lleno de clases. |
| 4 | 2026-10-10 | Supabase para Postgres, Auth y Storage; Drizzle como ORM en la API, con migraciones de drizzle-kit | Consultas explícitas y cercanas a SQL: el usuario quiere aprender fundamentos de bases de datos, y los filtros explícitos reducen el riesgo de "ORM leak". Prisma descartado (más magia, filtros muy flexibles). Solo la API toca la base. |
| 5 | 2026-10-10 | Datos totalmente aislados por usuario | Más simple y seguro. Compartir queda para más adelante. |
| 6 | 2026-10-10 | Registro solo por invitación | Es privado; nadie debe poder crear cuenta por su cuenta. |
| 7 | 2026-10-10 | ~~Login: correo + contraseña + código de 6 dígitos al correo~~ **Reemplazada por la 26.** | — |
| 8 | 2026-10-10 | Sesión de 30 días, con "cerrar sesión en todos los dispositivos" | El usuario deja la app abierta y no quiere entrar seguido. |
| 9 | 2026-10-10 | Avisos dentro de la app y Web Push en el navegador; nunca por correo | Preferencia del usuario. |
| 10 | 2026-10-10 | Finanzas solo en pesos (MXN); columna `currency` preparada | Conversión de monedas descartada por ahora. |
| 11 | 2026-10-10 | Temporadas: una festividad por mes, automática; solo cambian adornos | Lo más sencillo. Descartados cambios de paleta y animaciones por estación. |
| 12 | 2026-10-10 | El canvas de diseño es la fuente de verdad visual | El usuario lo seguirá editando. |
| 13 | 2026-10-10 | Primera versión en PC con todos los módulos; teléfono, modo oscuro, varios usuarios, sin conexión, exportar e integraciones después | Ver `docs/guides/roadmap.md`. |
| 14 | 2026-10-10 | Tests solo de lo crítico (seguridad, auth, cálculos) | Balance entre avanzar y no romper lo importante. |

| 17 | 2026-10-10 | Web y API desplegadas en Vercel (plan gratis). Tareas programadas: lógica en la API, disparadas cada minuto por Supabase Cron con un secreto | En Vercel la API no corre todo el tiempo, y el cron de Vercel gratis solo corre una vez al día. Descartados Railway, Render y Fly.io para no mantener otro servicio. |
| 18 | 2026-10-10 | El proyecto también es para aprender: estilo Learning de Claude Code activado y registro en `docs/learning/` | El usuario quiere aprender estructura y buenas prácticas construyéndolo. Ver la sección "Aprendizaje" de `CLAUDE.md`. |
| 19 | 2026-10-10 | GitHub Flow: `main` solo con lo revisado y funcionando, todo trabajo en ramas y Pull Requests; Conventional Commits con la descripción en español; commits y push solo con autorización del usuario | El usuario quiere controlar qué entra a `main` y usa la extensión Conventional Commits de VS Code. |
| 20 | 2026-10-10 | `apps/api` sin `@nestjs/cli` (sin `nest generate`/`nest build`); los archivos se escriben a mano, build con `tsc`, dev con `tsx watch` | `@nestjs/cli` 12.0.8 revienta con `ERR_REQUIRE_CYCLE_MODULE` en Node 22: bug de `@angular-devkit/schematics`, que carga `ora` (ESM) en un ciclo. No depende de la configuración del repo. Revisar si una versión futura lo arregla. |
| 21 | 2026-10-11 | `docs/guides/Kairo-Sistema-de-diseno.pdf` es la fuente exacta de tokens (color, tipografía, espacio, radios, sombras, componentes); `theming.md` solo describe la estructura de capas | El PDF trae valores de claro/oscuro y specs de componentes más precisos que lo que se podía sacar leyendo las pantallas `.dc.html` del prototipo. Cuando haya diferencia, manda el PDF. |
| 22 | 2026-10-11 | Las variables CSS semánticas se nombran en inglés (`--surface`, `--text-muted`, `--accent-soft`…), no con los nombres en español del PDF (`superficie`, `texto-2`…) | Consistencia con el resto del código (regla de idioma de `conventions.md`). El PDF queda como referencia de valores y significado, no de nombres de variable. |
| 23 | 2026-10-12 | Los enums de la base de datos se implementan como enums nativos de Postgres (`pgEnum` de Drizzle), no `text` + `CHECK` | Postgres valida el valor a nivel de columna. Se acepta la ceremonia extra de una migración `ALTER TYPE` cuando se agregue un valor nuevo. |
| 24 | 2026-10-12 | Proveedor de correo para invitaciones, código de login y recuperar contraseña: SMTP propio de Supabase | Evita depender de un servicio extra (Resend) mientras el volumen de correo es bajo (un solo usuario). Revisar si hace falta cambiar cuando haya varios usuarios o problemas de entrega. |
| 25 | 2026-10-13 | El guard global de la API verifica el JWT con `supabase.auth.getClaims()` (de `@supabase/supabase-js`), no con una librería de JWT/JWKS aparte | El proyecto ya usa llaves de firma asimétricas de Supabase (`sb_secret_...`); `getClaims()` verifica localmente contra el JWKS igual que lo haría `jose`, sin agregar una dependencia nueva. Si el proyecto usara llaves simétricas (HS256), este método llamaría al servidor de Supabase en cada petición. |
| 26 | 2026-10-13 | Login: solo correo + contraseña por ahora, sin segundo factor. Código por correo pasa a "Después" (`docs/guides/roadmap.md`) | Construirlo ahora exige infraestructura de correo propia en la API (SMTP o Resend) que todavía no existe (igual que la invitación a otras personas, ver #24), más rate limiting, intentos y una pantalla nueva. Para una cuenta de un solo usuario invitado, correo + contraseña es razonable mientras tanto. Las tablas `login_codes` y `verified_sessions` se quedan sin usar, listas para cuando se retome. Reemplaza la 7. |
| 27 | 2026-10-16 | En la rutina, un bloque se marca "tarde" si se marca después de que ya se insistió (hora del bloque + los minutos de "Si no lo marco, insistir"). Sin insistir: al terminar el bloque o, si es un momento sin hora de fin, a los 30 minutos | El canvas dice "hecho tarde, después del aviso" (Reporte) pero no define la regla; se dedujo de la opción "insistir" del editor de bloques. Los 30 minutos de gracia son una decisión nuestra para el caso que el canvas no cubre. La hora de la marca y si fue tarde las decide el servidor, no la pantalla. Vive en `lateFromMinutes` (`features/daily/routine-utils.ts`). |
