# 2026-10-18 · Fase 1b: Día a día (rutina, menú, diario y metas)

**Hecho en:** Claude Code

## Qué se hizo

Cuarto módulo de Fase 1b, y el más grande de los cuatro: las 4 partes de Día a día (Rutina/Hoy, Menú semanal, Diario, Metas) reconectadas de una sola vez, a pedido explícito de la usuaria ("has tu todo ya sabes, solo me entregas el resultado final").

- **Esquema nuevo** (`apps/api/src/db/schema/daily.ts`, migración `0006`): `routines`, `routine_blocks`, `routine_logs`, `meal_plans`, `journal_entries`, `goals`, `goal_milestones`, `goal_log_entries`. Un solo módulo de Nest (`apps/api/src/modules/daily/`) con un controller/service/repository por área (`routines.*`, `meals.*`, `journal.*`, `goals.*`) y un `DailyUndoController`/`DailyUndoService` compartido para las 4.
- **La API solo persiste y devuelve hechos crudos.** `routine_logs` guarda, por bloque y día, la hora de la marca, si fue tarde y cuántas tareas de enfoque van; el cálculo de reporte (`cellState`, `reportStats`), rachas (`streakLength`/`streakDots`) y el avance de una meta de hábito (`habitRate`) se queda en el Next.js de en medio (`routine-utils.ts`/`api.ts`, sin tocar su lógica), igual que ya se había decidido para Agenda (#37). Lo mismo para las metas: `deriveGoal` sigue recalculando al leer el avance de una meta de hitos, de proyecto o de hábito; la API solo guarda la fila y sus hitos/registro de avance.
- **Un solo Deshacer para las 4 áreas.** El front ya compartía una sola `undoRoutineAction(token)` para borrar un bloque, una rutina, un platillo, una entrada del diario o una meta; la API expone `POST /daily/undo` con un token de acción codificada (`daily-undo.ts`, mismo patrón de las decisiones 36/37) que decide a cuál de los 4 repositorios avisar.
- **El Diario se conectó sin PIN ni cifrado** (decisión #39, explícita de la usuaria, en contra de lo que pedía `docs/guides/security.md`): `journal_entries.body` se guarda en claro.
- **Lo que se quedó de ejemplo a propósito:** la "siguiente tarea" de un bloque de enfoque (`FOCUS_TASKS`, en `mock.ts`, usado en ambos modos) porque Tareas no tiene el concepto de "área" para filtrar por ahí; los extras del resumen del día del Diario (tareas hechas, eventos); y `has_event` de un platillo del menú (siempre `false` al leer, como `project: null` en Tareas/Agenda) porque Agenda todavía no tiene datos reales.
- **Un detalle de Postgres que costó una vuelta:** una columna `time` devuelve `'HH:MM:SS'` al leer (con segundos) aunque se guarde como `'HH:MM'`; se normaliza al mapear la fila a la respuesta (`toWallTime`, `daily-utils.ts`) para no romper el contrato que ya esperaba el front. También: devolver `null` directo desde un controller de Nest no serializa como JSON `null` (el cliente recibe un cuerpo vacío); donde hacía falta (guardar un platillo con `dish` vacío) se envolvió en `{ plan: null }`.
- Front: `features/daily/api.ts` y los 4 `*-actions.ts` (`routine-`, `meal-`, `journal-`, `goal-actions.ts`) reescritos con el mismo contrato (`DailyActionResult`); `mock-store.ts` se borró (ya no se usa, las Server Actions siempre llaman a la API real, igual que en Recordatorios/Agenda); `mock.ts` se queda para el modo demo (y para `FOCUS_TASKS`/los extras, en ambos modos).

## Decisiones tomadas

- **#38:** la API de Día a día solo guarda hechos crudos; reporte, rachas y avance de meta de hábito siguen en el front. Un solo endpoint de Deshacer para las 4 áreas. `project_id`/`link` sin FK (mismo patrón que 35-37); `block_id` en `goals` sí lleva FK (mismo módulo). Focus→Tareas, Diario→extras y Menú→Agenda se quedan de ejemplo.
- **#39:** el Diario se conecta sin PIN ni cifrado, a pedido explícito de la usuaria, en contra de `security.md`. Pendiente de reforzar si se decide más adelante (`profiles.diary_pin_hash` ya existe sin usarse).

(El detalle completo de cada una está en `docs/guides/decisions.md`.)
